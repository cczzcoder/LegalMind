## 1. 总体设计原则

- 原文与元数据是权威数据，索引是可重建的派生数据
- 法律版本与 Wiki 编辑修订分别建模
- 权限在检索前、证据装配时及输出前执行
- 模型不直接修改正式知识、不直接执行数据库操作
- 高耗时任务异步执行，但最终状态持久化到数据库
- 正式答案通过核验后输出，未核验内容不提前流式展示
- 第一版采用模块化单体，不拆分大量微服务
- 不以哈希链、多模型一致或某个评分作为绝对正确性证明

## 2. 技术选型基线

以下为本项目设计选型，不代表相关组件未经测试即可满足全部需求。

| 层级 | 选型 |
| --- | --- |
| 后端 | FastAPI + Pydantic v2 |
| 数据访问 | SQLAlchemy 2.x + asyncpg |
| 数据库迁移 | Alembic |
| 主数据库 | PostgreSQL |
| 内部管理 | SQLAdmin，限制为运维及受控管理入口 |
| 业务前端 | React + TypeScript + Ant Design |
| 认证 | 同源 Web 默认服务端会话；预留 OIDC 适配接口 |
| 授权 | 自建 AuthorizationService + RBAC + 对象级授权 |
| 后台任务 | Celery + Redis Broker |
| 关键词检索 | Elasticsearch + 经兼容性验证的中文分词 |
| 向量检索 | Qdrant |
| 原文存储 | 经评审的 S3 兼容对象存储 |
| Wiki | 自建业务模块，PostgreSQL 保存修订与引用 |
| 解析 | DocumentParser 接口，解析器经样本测试后锁定 |
| Embedding / Reranker | 可替换适配器，按评测选择 |
| 生成及语义核验 | 模型网关统一调用 |
| RAG 编排 | 自建显式流水线 |
| 评测 | pytest + 人工金标准 + RAGAS |
| 可观测性 | 结构化日志、指标、请求与任务追踪 |
| 部署 | Docker Compose |

**选型约束：**

- 不使用未经验证的“最新版本”组合；锁定兼容版本和镜像摘要
- 核查组件许可、模型许可及数据使用限制
- 对象存储、模型和解析器未通过验收前，只作为可替换适配层
- Elasticsearch 与 Qdrant 是不同检索通路；初版不再额外重复维护第三套稀疏检索

## 3. 总体架构

```text
浏览器
  │ HTTPS
反向代理
  │
FastAPI
  ├─ 认证与授权模块
  ├─ 来源与资料模块
  ├─ 法律版本模块
  ├─ Wiki 与审核模块
  ├─ 检索与问答模块
  ├─ 审计与评测模块
  └─ 任务与配置模块
       │
       ├─ PostgreSQL：业务权威记录、版本、权限、任务、审计
       ├─ 对象存储：原件、解析产物、归档、备份
       ├─ Elasticsearch：精确字段与关键词索引
       ├─ Qdrant：向量及过滤元数据
       └─ 模型网关：Embedding、Reranker、生成、语义核验

PostgreSQL Outbox
  │
投递器 → Redis → Celery Workers
                    ├─ 文件解析
                    ├─ 索引构建
                    ├─ 问答执行
                    ├─ 更新检查
                    └─ 评测与归档
```

API 服务不执行长时间 OCR、批量 Embedding 或完整索引重建，这些工作由 Celery Worker 承担。

## 5. 核心数据模型

### 5.1 主要实体

| 实体 | 关键字段或关系 |
| --- | --- |
| Organization | 机构及隔离范围 |
| User / Role / Permission | 身份和操作权限 |
| AccessGrant | 用户或组对资源的授权 |
| Source | 来源、可信等级、授权说明、核查时间 |
| SourceArtifact | 对象键、哈希、来源、类型、采集时间 |
| ParseRevision | 文件、解析器版本、文本哈希、质量状态 |
| LegalInstrument | 名称、法域、机关、资料类型、稳定 ID |
| LegalVersion | 文件 ID、公布/生效/失效信息、审核状态 |
| ProvisionIdentity | 条款稳定身份 |
| ProvisionVersion | 法律版本、条款身份、原文及结构路径 |
| ProvisionRelation | 替代、改号、拆分、合并、引用等关系 |
| ApplicabilityRecord | 适用规则、范围、依据及确认状态 |
| Chunk | 解析版本、结构范围、文本、原文定位 |
| WikiPage | 标题、分类、访问范围、当前发布修订 |
| WikiRevision | 修订号、正文、发布状态、依据状态 |
| Claim / Citation | 主张与具体证据版本及片段关系 |
| ReviewRecord | 对象、决定、理由、审核者和时间 |
| AnswerRun | 问题、状态、配置、证据集及核验结果 |
| AuditEvent / OutboxEvent | 审计及可靠事件投递 |
| IndexBuild | 索引代次、模型版本、数据水位及状态 |
| EvaluationRun | 测试集版本、配置和结果 |

### 5.2 版本关系

```text
LegalInstrument
  ├─ LegalVersion
  │    └─ ProvisionVersion
  └─ ProvisionIdentity
       └─ ProvisionVersion

SourceArtifact
  └─ ParseRevision
       └─ Chunk

WikiPage
  └─ WikiRevision
       └─ Claim
            └─ Citation
                 ├─ ProvisionVersion
                 └─ SourceSpan
```

### 5.3 数据约束

- 正式内容修订不可原地覆盖；纠错生成新修订并关联旧记录
- 引用必须绑定不可变版本，不得只绑定“最新页面”
- 日期未知应显式存储“未知”，不虚构日期
- 法律效力时间按法律日期处理，系统事件统一使用带时区时间戳
- 用明确的数据约束防止重复版本和孤立引用
- 同一条款发生拆分或合并时允许多对多映射
- 不对所有法律版本简单施加“不允许时间重叠”，复杂适用关系应单独表达

## 6. 原文定位设计

建议使用：

```json
{
  "artifact_id": "artifact-uuid",
  "artifact_sha256": "...",
  "parse_revision_id": "parse-uuid",
  "page_index": 12,
  "printed_page_label": "10",
  "block_id": "block-uuid",
  "char_start": 120,
  "char_end": 186,
  "coordinate_system": "normalized-page",
  "bbox": [0.12, 0.25, 0.88, 0.41],
  "text_sha256": "..."
}
```

**约定：**

- `page_index` 为原始文件零基页序号
- 印刷页码独立保存，不与文件页序号混用
- 字符偏移相对于指定解析版本的规范化文本，以 Unicode 码点计数
- 跨页片段使用多个 SourceSpan
- HTML 使用内容快照及 DOM/文本定位，不强制生成页码
- 解析文本更新时创建新定位版本，不静默移动既有引用

## 7. 入库流水线

```text
接收文件
  → 安全及授权检查
  → 保存原件和哈希
  → 建立导入任务
  → 解析/OCR
  → 结构化识别
  → 质量检查
  → 必要的人工校正
  → 版本关联确认
  → 分块与原文定位
  → Embedding
  → 构建关键词及向量索引
  → 一致性检查
  → 激活检索版本
```

### 7.1 幂等性

任务唯一键建议包含：

```text
组织 + 文件哈希 + 任务类型 + 处理配置版本
```

任务状态持久化到 PostgreSQL，不把 Celery 返回值作为唯一业务状态。

### 7.2 索引一致性

PostgreSQL、Elasticsearch 和 Qdrant 不按单个跨系统事务设计，采用：

1. 数据库提交正式记录及 Outbox 事件
2. Worker 构建新索引代次
3. 校验记录数、哈希、版本和权限元数据
4. 数据库切换 `active_index_build_id`
5. 查询同时携带被选定的索引代次
6. 延迟清理旧索引，保留回滚窗口

构建失败不得破坏当前可用索引。

## 8. 检索设计

### 8.1 查询输入

```json
{
  "question": "问题正文",
  "jurisdiction": "指定范围",
  "fact_date": "2024-01-15",
  "mode": "historical",
  "source_types": ["regulation", "interpretation"],
  "conversation_id": "optional"
}
```

用户身份、组织和授权范围由服务端确定，不信任客户端提交的权限字段。

### 8.2 检索步骤

1. 保留原始查询并生成受约束的补充查询
2. 提取法域、日期、名称、条号及缺失事实
3. 构造授权、发布状态和资料范围过滤
4. 分别执行精确查询、关键词检索和向量检索
5. 按条款版本及内容哈希去重
6. 使用 RRF 等方法融合候选
7. 重排序
8. 扩展完整条款、定义、例外及关联依据
9. 再次授权并组成证据集

**初始实验参数建议**（必须由评测调整）：

- 关键词与向量各召回 50 条
- 合并后最多重排 100 条
- 选取约 10～20 个证据单元
- 超出上下文预算时按主张覆盖选择，不直接截掉例外

### 8.3 精确字段与过滤

- 文号、稳定 ID、规范化条号使用 `keyword` 字段，正文与标题另设全文字段。Elasticsearch 官方将 `keyword` 用于结构化值及精确匹配场景，不能只依赖中文分词实现文号匹配。（[elastic.co](https://www.elastic.co)）
- Qdrant 中保存组织、访问范围、发布状态、版本及索引代次等过滤元数据；其过滤机制用于检索范围约束，但最终授权仍由应用负责。（[qdrant.tech](https://qdrant.tech)）

## 9. 问答与核验设计

### 9.1 执行状态

```text
CREATED
 → CLARIFYING / RETRIEVING
 → RERANKING
 → ASSEMBLING_EVIDENCE
 → GENERATING
 → VERIFYING
 → ANSWERED / PARTIAL / NEEDS_REVIEW
             / INSUFFICIENT_EVIDENCE / FAILED
```

### 9.2 模型输出约束

模型仅输出结构化主张和允许的证据 ID：

```json
{
  "claims": [
    {
      "claim_id": "c1",
      "text": "限定范围内的结论",
      "evidence_ids": ["e1", "e2"],
      "conditions": ["前提条件"],
      "limitations": ["尚未确认事项"]
    }
  ],
  "missing_facts": [],
  "conflicts": []
}
```

服务端负责生成引用标题和访问入口，不接受模型自行生成的来源链接作为有效证据。

### 9.3 三层核验

**第一层：确定性校验**

- 引用 ID 是否存在于本次授权证据集
- 引文是否匹配固定版本
- 证据是否发布、可访问且未被撤回
- 日期、文号、条号是否一致
- 数值是否来自输入或明确证据
- 已确认的适用范围是否匹配

**第二层：语义校验**，逐项判断：

- 证据是否支持主张
- 是否遗漏条件、例外或相反依据
- 是否存在过度概括
- 是否将不同资料类型的权威程度混淆

**第三层：人工审核**，处理：

- 未解决的依据冲突
- 复杂时间适用
- 高风险个性化判断
- 重要解析疑点
- 无法自动核验的计算前提

金额与期限计算使用明确规则和确定性程序；规则选择不清楚时转人工，不交给模型自由计算。

### 9.4 输出控制

- SSE 只在核验前发送进度状态，正式答案通过门禁后发送
- 语义核验模型不可用时，不跳过核验发布完整结论；可返回检索资料或进入待审状态
- 问答记录保存证据和配置快照，不要求保存或展示模型隐藏推理过程

## 10. Wiki 设计

### 10.1 页面内容结构

```text
标题及别名
主题范围
适用法域与时间范围
概念和规则说明
条件与例外
争议和不同观点
原文依据
相关页面及反向链接
审核信息
```

### 10.2 发布规则

- 编辑修改生成新修订
- 提交后锁定该修订，后续修改创建新修订
- 审核通过后更新当前发布指针
- 引用检查不通过不得发布
- 来源更新先标记待复核，不自动删除历史说明
- 原文更新不得由 AI 直接覆盖已发布结论

### 10.3 权限继承

- Wiki 修订的读者必须对其受限来源具有相应访问权
- 公开化必须经过独立审核，不能因为内容被概括或改写就自动取消原文限制

## 11. 认证、权限与安全设计

### 11.1 身份认证

第一版默认采用同源 Web 服务端会话：

- Cookie 设置 HttpOnly、Secure 及适当的 SameSite
- 写操作执行 CSRF 防护
- 管理员使用 MFA
- 支持会话撤销和用户禁用
- 预留 OIDC 登录适配
- 外部 API 如需令牌，另行设置 scope 和生命周期

### 11.2 授权流程

```text
请求进入
  → 验证身份与角色
  → 构建对象访问范围
  → 检索过滤
  → 数据库复核候选对象权限
  → 模型上下文检查
  → 输出/下载再次检查
```

缓存键至少纳入：

```text
组织 + 授权范围指纹 + 权限版本
+ 查询条件 + 索引版本 + 模型/提示词版本
```

第一版不启用跨用户语义答案缓存。

### 11.3 AI 与文件安全

- 文档正文视为不可信数据，不作为系统指令
- 检索与生成模型不具备数据库写权限
- HTML、Markdown 和模型输出经过安全渲染
- 采集器限制目标域、重定向和内网地址访问
- 文件解析在受限环境中执行，并限制时间、内存和解压大小
- 外部模型调用按资料分级控制
- 日志脱敏，密钥不进入源码、提示词或普通审计正文

这些措施针对包括间接提示注入在内的风险。OWASP 强调隔离不可信内容、限制工具权限及分层防护，不能只依赖一段“忽略恶意指令”的提示词。（[cheatsheetseries.owasp.org](https://cheatsheetseries.owasp.org)）

## 12. 审计、Outbox 与任务可靠性

### 12.1 同事务写入

关键业务操作在同一个 PostgreSQL 事务中写入：

```text
业务变更 + AuditEvent + OutboxEvent
```

外部模型调用、文件处理和队列发送不放在长数据库事务内。

### 12.2 投递与消费

- 采用至少一次投递和幂等消费
- 事件具有唯一 ID
- 发布状态与任务业务完成状态分别记录
- 定时对账未完成事件与失联任务
- 重试次数、退避、最大执行时间可配置
- 永久失败进入人工处理队列

Redis Broker 的可见性超时可能导致未确认任务重新投递，因此配置必须结合实际最长任务，并仍然保证幂等，不能仅靠拉长超时避免问题。（[docs.celeryq.dev](https://docs.celeryq.dev)）

### 12.3 数据库会话

API 请求和各并发任务使用独立会话，不跨线程或并发任务复用 AsyncSession。SQLAlchemy 官方明确采用“每个 asyncio 任务一个 AsyncSession”的并发方式。（[docs.sqlalchemy.org](https://docs.sqlalchemy.org)）

### 12.4 防篡改措施

- 审计表对应用账号禁止更新、删除
- 按组织或分区构建哈希链，定期生成外部校验点并归档
- 哈希链用于辅助检测，不作为抵抗数据库高权限攻击的唯一措施

| `POST /api/v1/answer-runs` | 创建异步问答 |
| `GET /api/v1/answer-runs/{id}` | 查询答案及核验状态 |
| `GET /api/v1/answer-runs/{id}/events` | SSE 进度 |
| `POST /api/v1/wiki/pages` | 新建页面 |
| `POST /api/v1/wiki/pages/{id}/revisions` | 创建修订 |
| `POST /api/v1/wiki/revisions/{id}/submit` | 提交审核 |
| `POST /api/v1/reviews/{id}/decision` | 审核决定 |
| `GET /api/v1/citations/{id}` | 授权后查看证据 |
| `POST /api/v1/evaluation-runs` | 执行评测 |

**约定：**

- 创建型长任务返回 `202 Accepted` 和任务 ID
- 幂等创建使用 `Idempotency-Key`
- 编辑使用修订号或 `If-Match` 防止覆盖
- 分页使用游标并限制单次返回量
- 错误返回统一包含 `code`、安全描述和 `trace_id`
- 对无权访问的资源采用一致响应策略，避免泄露其存在性

## 14. 部署与配置

### 14.1 服务划分

```text
reverse-proxy
api
worker-parse
worker-index
worker-answer
worker-maintenance
scheduler / outbox-dispatcher
postgres
redis
elasticsearch
qdrant
object-storage（或外部服务）
monitoring
```

可在同一台机器上运行，但需限制并发，避免 OCR、建索引和问答争抢全部资源。

### 14.2 网络与密钥

- 仅反向代理对外暴露业务入口
- 数据库、队列及检索服务置于内部网络
- 非敏感配置使用环境变量
- 生产密钥使用受控挂载或专门密钥管理，开发 `.env` 不提交仓库
- 备份凭据与业务服务凭据分离

### 14.3 容量确定

不把 32 GB 内存或 500 GB SSD 写成正式需求。先测量：

```text
原始资料容量
+ 解析产物
+ PostgreSQL 数据及日志
+ 全文索引
+ 向量及索引结构
+ 新旧索引并存
+ 临时文件
+ 备份与恢复空间
```

本地模型和 GPU 资源单独估算，容量按实测增长及重建峰值预留余量。

## 15. 备份、恢复与数据生命周期

### 15.1 备份策略

| 数据 | 设计策略 |
| --- | --- |
| PostgreSQL | 基础备份、WAL 归档和定期恢复验证 |
| 原始文件 | 版本化保存、异机副本及哈希校验 |
| Elasticsearch | 快照及可重建配置 |
| Qdrant | 快照及可重建向量/模型记录 |
| 配置和迁移 | 版本化保存 |
| 密钥 | 独立受控备份和恢复权限 |
| 审计 | 按保留政策归档 |

PostgreSQL 的连续归档与时间点恢复需要基础备份及相应 WAL；普通 `pg_dump` 不等同于这套 PITR 机制。（[postgresql.org](https://www.postgresql.org)）

### 15.2 恢复顺序

1. 恢复密钥及受控配置
2. 恢复数据库与原文对象
3. 校验文件清单、哈希和引用
4. 恢复或重建检索索引
5. 校验权限及发布状态
6. 对账任务、Outbox 和审计
7. 运行关键测试
8. 恢复对用户服务

若索引快照与数据库恢复点不一致，应重新对账或重建，不直接对外开放。

### 15.3 删除与保留

需区分：

- 撤回发布
- 用户不可见
- 历史归档
- 到期物理删除
- 暂停删除的保留要求

删除流程必须覆盖原件、解析产物、索引、缓存和衍生 Wiki；备份中的数据按既定生命周期处理，并防止恢复后重新暴露已删除资料。

具体保留年限由组织政策及适用要求确认，不在技术文档中自行设定。

## 16. 可观测性与故障降级

### 16.1 监控项目

- 入库成功率、解析失败率
- 来源检查逾期时间
- 索引同步延迟
- 任务积压、重试和永久失败
- 数据库连接、磁盘和内存
- 检索及问答各阶段耗时
- 无结果、拒答、人工复核比例
- 引用核验失败率
- 模型调用失败、费用及数据外发记录
- 备份完成时间及恢复演练结果

### 16.2 降级策略

| 故障 | 处理 |
| --- | --- |
| 生成模型不可用 | 保留授权检索，不生成结论 |
| 语义核验不可用 | 返回资料或待审核状态 |
| 部分检索服务不可用 | 标明检索不完整；正式问答按门禁暂停 |
| 索引更新失败 | 使用仍合格的旧索引并提示时效，必要时停止回答 |
| 授权服务或数据库不可用 | 默认拒绝，不使用旧权限放行 |
| 原文无法访问 | 对受影响证据阻止正式引用 |
| 审计写入失败 | 关键变更回滚或拒绝执行 |
