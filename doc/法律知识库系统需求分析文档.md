## 版本调整说明

V1.2 以个人笔记本作为第一阶段开发和试验环境。现有设备配置为 AMD Ryzen 7 7735H、16 GB 内存、512 GB SSD、RTX 4060；可用磁盘空间和实际专用显存以运行环境检测结果为准。

本次调整聚焦部署资源与实现复杂度，**不降低**法律资料版本管理、原文追溯、访问控制、Wiki 审核、证据核验及评测要求。

第一阶段采用模块化单体、单任务并发、按需加载模型和最少常驻服务。独立检索服务、分布式任务队列和对象存储服务根据后续评测结果引入，引入条件见《系统设计文档》第 18 节。

### V1.3 调整（2026-10-03）

本版确认检索与问答的编排及图谱增强检索选型（详见《系统设计文档》第 2、8.4 节）：

- **RAG 编排**：采用 **LangGraph 状态图编排 + LangChain 组件库**，替代原“自建显式流水线”设想。
- **图谱增强检索（GraphRAG）**：引入知识图谱提升检索精度；第一阶段在 PostgreSQL + pgvector 上概念验证，**准确率评测达标后**再迁移 Neo4j。
- 多智能体仍不在第一版范围。

本次调整不改变 FR-01 至 FR-13 的功能要求，也不降低第 6 节的准确性、权限和审计验收标准。

### V1.4 调整（2026-10-03）

明确系统的合规定位，把风险控制前置到需求与架构设计：

- **产品定位**：本系统是**法律信息辅助工具**，不是法律服务提供方。系统输出不构成法律意见，不得用于替代执业律师判断或直接对外出具法律结论。
- **主要风险**：① 无资质提供法律服务；② 资料采集侵犯知识产权或不正当竞争；③ 模型生成错误内容引发责任。
- **控制要求**：数据来源优先官方渠道或已获商业授权；保留授权说明与核查记录；引用必须可溯源到具体版本；正式结论必须经人工审核。

风险不在“建库”本身，而在“如何使用”。对应功能要求见 FR-14，架构控制见《系统设计文档》第 20 节。

本配置是开发与试验基线，不构成生产容量、可用性或安全保证。

### V1.5 调整（2026-10-03）

明确数据边界与租户形态，把范围收窄到可交付的第一版：

- **数据范围**：系统只存放**公共法律数据**（法律法规、司法解释、公开裁判文书），**不存放任何客户资料与具体案件数据**。需求 2.2 中“是否包含客户资料或其他敏感信息”据此确认为**否**。
- **租户形态**：第一版为**单租户、部门级内部工具**，目标是跑通“原生解析 → 检索（含 GraphRAG 概念验证）→ 证据约束问答”的闭环。**SaaS 多租户划入远期规划（V2.0）**，引入前须满足《系统设计文档》第 18 节触发条件。
- **数据准入网关**：解析完成后、入库前须经脱敏节点，当事人姓名、身份证号、案号等实体替换为占位符。采用**先定位、后脱敏**并保留可逆映射（见 FR-15、《系统设计文档》第 21 节）。
- **审计边界**：审计只记录元数据与哈希，不记录请求或回答正文。

本次调整**不放宽** 1.2 的使用边界与 FR-14 的合规要求；脱敏与访问控制不因“数据已公开”而免除。

### V1.6 调整（2026-10-03）

明确文档解析的分层范围与准入条件（对应《系统设计文档》第 2、6、17.2 节）：

- **解析分三层**：第 1 层原生解析（纯 CPU、零外发、许可宽松）；第 2 层 OCR（扫描件/图片型 PDF 的文字识别）；第 3 层结构化版面理解（Docling 等）。
- **第一版只交付第 1 层**：PDF（双后端）、DOCX、HTML、纯文本。**第 2 层 OCR 与第 3 层 Docling 不在本版范围**；Docling 明确暂缓，避免拉取大模型权重造成镜像膨胀与维护成本，待 P4 检索确需表格结构化时再评估。
- **扫描件处理边界**：取不到文本层的页标记 `needs_review`，**不伪造文本**；在 OCR 就位前，扫描件不得作为检索与问答的证据来源。
- **定位要求**：解析产物须能定位到页、块与字符区间，`bbox` 归一化到页面坐标；印刷页码等未知信息存“未知”，不虚构（对应 FR-06 的原文追溯要求，与《系统设计文档》第 6 节一致）。
- **资源受限**：解析须在 16 GB 单机档位内完成，逐页处理并设置字节/页数/字符数上限与内存守卫；资源不足时排队或降批次，不跳过核验（FR-13）。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不降低第 6 节的准确性、权限与审计验收标准。

### V1.7 调整（2026-10-03）

确认第 1 层解析选型，并落实 FR-15 的脱敏准入：

- 第 2 层 OCR 与第 3 层 Docling 仍不在本版范围。

本次调整不改变 FR-01 至 FR-15 的功能要求。

### V1.8 调整（2026-10-03）

实现按需启动的后台 worker，使"导入 → 解析 → 入库"自动闭环（FR-02、FR-06、FR-13）：

- 导入登记的任务由 worker 自动领取执行，不再需要人工触发。
- 失败区分**确定性失败**（原件缺失、超出解析上限、解析被拒 → 进入人工处理）与**可重试失败**（原件暂不可用、内存超预算 → 退避重试）；**资源不足记录明确的错误码，不伪装成成功**（FR-13）。

- 单进程单并发，任务结束即释放资源，符合 FR-13 的资源受限运行模式。

本次调整不改变 FR-01 至 FR-15 的功能要求。

### V1.9 调整（2026-10-03）

落地法律结构识别，使条款级检索与引用具备基础（FR-06 原文追溯）：

- **识别 编/章/节/条** 四级结构，并把分块对齐到「条」——检索与引用以条为最小单位，每个分块自带章节路径。
- **款/项/目 暂不建模**：款无编号，扫描/逐行解析下与普通换行无法区分；项（`（一）`）的嵌套位置依赖款。这些文本仍完整保留，只是不单独建身份。
- **条款身份只覆盖「条」**：实测条号全文连续，可作为稳定身份；章号、节号会随上级重置，无法稳定标识，只作结构路径。这不影响 FR-06 的"可追溯到具体条款"要求——引用以条为单位。
- **不得虚构结构**：识别不到结构时按普通文本处理，不臆造条款；条号不连续只记录提示，不静默修正。

本次调整不改变 FR-01 至 FR-15 的功能要求。

### V1.10 调整（2026-10-03）

落地法律版本落库，使"引用绑定具体版本"具备数据基础（FR-06、FR-07）：

- **版本可追溯**：解析结果自动挂到法律本体与版本上；版本标识取自正文公布信息（`2018年修正` / `2026年修订` / `2026年`），取不到才回退文件名，并标记为低置信度。
- **效力状态不得虚构**：版本效力状态由公布信息的施行日期推导为「当前有效」/「已公布未生效」，取不到记「未知」而不推断。**「已公布未生效」的版本入库以供溯源，但默认不进入检索结果**——不得把尚未生效的法律当作现行依据（FR-06、FR-09）。
- **自动确认不等于人工审核**：正文提取完整且无冲突时自动确认；版本标识来自文件名回退、标题退化为文件名、或同一版本出现多个原件时，一律置为**待审核**并写审计事件。人工确认的界面与待审队列尚未实现，属已知缺口，已在设计文档 §17.2 记录。
- **条款身份仍只覆盖「条」**（与 V1.9 一致）；条款文本同样存脱敏文本、绑该条首个分块，编/章/节只作结构路径。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不改变验收标准。

### V1.11 调整（2026-10-04）

落地精确字段检索，并补入库质量门禁校验（FR-05、FR-06、FR-09、FR-14）：

- **精确检索已实现**：按名称、文号、稳定 ID、规范化条号精确匹配，叠加法域、资料类型、效力日期与授权过滤。写入与检索共用同一套规范化口径（文号去空白、全角转半角、「第X号」中文数字转阿拉伯数字；条号接受「第八十七条」「87」「第八十七条之一」）。
- **「已公布未生效」默认不进入检索结果**（落实 V1.10 的要求，FR-06、FR-09）：把尚未生效的法律当作现行依据是最危险的错误；需要核对未来或历史版本时显式放开。
- **审核状态不过滤、但必须回传**：`pending` 是数据质量标记，不是法律效力事实——默认按它过滤会把确实存在、只是尚未人工确认的法律整条藏起来。回答层据此判断能否下结论。
- **授权在数据库里复核**（FR-10）：检索结果先 join 原件并套授权范围，不信任调用方提交的范围。
- **入库质量门禁**：对来源、元数据与解析质量做一次只读校验，把每个原件判为通过 / 降级待审 / 不通过——硬要求（来源登记与授权说明、解析产物、挂到版本）不过即不通过。**门禁只校验，不阻断**。
- **来源分级登记**（FR-14）：官方公开文献属公共数据，登记来源凭证即可；商业数据库须标注商业授权。**版权声明与 ICP 备案不是授权说明**。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不改变验收标准。

### V1.12 调整（2026-10-04）

补齐**中文关键词检索**，让「查得到」不再只依赖精确字段（FR-05）：

- **方案由测试集选型，不凭感觉定**：先建 28 条金标准（查询 → 期望条款），期望集由「去空白文本包含全部查询词」**推导**得出，避免人工标注出错；再横向比较 5 个候选，选中「去空白 + 多词 AND」（召回与准确率均为 1.0）。
- **折行空格必须处理**：条款文本里夹着折行空格（实测「民用航 空器」），按原文直接子串匹配会**丢掉一半目标**（实测召回 0.5 → 处理后的 1.0）。这是对**采集与解析质量**的要求，不只是检索实现细节。
- **不引入新组件**（FR-13 资源受限运行模式）：PostgreSQL 自带的全文检索切不出中文词（默认解析器把整段中日韩字符当成一个词元），而 pg_trgm 只解决速度、当前规模未达引入条件。因此**不引入 Elasticsearch**。
- **关键词与精确字段是叠加关系**，不是二选一；语义检索（同义改写、自然语言提问）仍待向量通路，不在本版。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不改变验收标准。

### V1.13 调整（2026-10-04）

补齐**向量检索**与**查询改写**，让「查得到」不再被措辞限制（FR-05）：

- **本地嵌入模型，数据不外发**（§9.5 的硬要求）：条款文本与向量都不出本机。
- **先建问句式金标准再选模型**：24 条自然语言问题。该集合上关键词检索召回为 **0**，BGE-M3 为 **1.0**、text2vec 为 0.917，**故选定 BGE-M3**——用体积换召回，对「条文一条都不能漏」这个场景是划算的。
- **两条通路都要，不是二选一**：词面查询靠关键词（词面金标准上 Recall / 准确率 1.0，向量精确率只有 0.030），口语提问靠向量（召回 1.0、关键词为 0）。**实现成级联**（先关键词、命中为空再走向量兜底）而不是简单融合——不用 RRF 的实测依据是**候选集合膨胀**（词面集关键词段平均 1.5 条/查询、RRF 43.9 条，前 5 条 70% 是噪声，会挤占下游证据预算）与**排序被弱通路拖坏**（简称集 Rank@1 0.889 → 0.309）。⚠️ 早先引用的「准确率 1.0 → 0.035」分母是返回条数、会随 top-k 漂移，**已废弃不再引用**。
- **查询改写解决简称**：用户输入「社保」时语料里**一条都没有**，改写为「社会保险」后命中 13 条；但改写**跨不过语义鸿沟**，那一层仍要向量通路。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不改变验收标准。

### V1.15 调整（2026-10-05）

补齐 **Wiki 审核发布**（设计第 10.2、10.3 节），并补上需求第 3 节一直缺的两个角色权限：

- **审核发布是状态机**：草稿 → 提交 → 发布 / 驳回。提交即锁定，改正文要新开修订；驳回后可以**只补引用**再提交。

- **待审队列**已有接口，不再是「只能用 SQL 查」。

- **明确不做**：指代消解、会话列表/管理界面、**会话历史落库（是「不做」不是「暂缓」）**。
- **已实现**（同版本）：`answering/session.py`（`compose_query` / `read_turns` / `record_turn`）+ `answer_question(session_id=)` + `POST /answers` 的可选 `session_id` + CLI `ask --session`；测试 `tests/test_session.py`（16 项）。**实测**：同一句「那如果是这样呢？」，带会话时检索到与上一轮相同的《劳动法》第一百条并给出同样结论；**不带会话时检索到完全无关的法律**，模型编出的主张被引用核验拦下、不作为正式答案发布。

本次调整不改变 FR-01 至 FR-15 的功能要求，也不改变验收标准。

### V1.40 调整（2026-10-08）

**给「不用 RRF」换一个站得住的论据。**

此前本文第 5 节与另外三份文档都用「实测 RRF 会把关键词的准确率从 1.0 拉到 0.035」来论证否决
RRF。复核后发现那个指标是 `精确率 = Σ命中 / Σ返回条数`，**分母就是返回条数**——同一个 RRF 在
`--top-k 20 / 60` 下分别报出 0.076 / 0.035，它度量的是**候选集合大小**，不是排序质量；而级联与
RRF 在词面金标准上的 **Recall / Rank@1 / MRR 完全一致（都是 1.000）**。

- **不用 RRF 的真实依据**（实测，见《系统设计文档》§8.2 与 `doc/技术决策与踩坑记录.md` §1.7）：
  ① **候选集合膨胀**——词面集关键词段平均只交 1.5 条/查询（全部命中），RRF 交 43.9 条，前 5 条里
  70% 是噪声，会挤占下游的证据预算；② **排序被弱通路拖坏**——简称集 Rank@1 从 0.889 掉到 0.309
  （与向量单独跑同分），召回从 85 条掉到 72 条。
- **级联的收益来自「路由」而非「融合」**：问句式集上级联 = 向量 = RRF 三项完全同分。级联只做
  一件事——**关键词有命中时不去跑向量**。
- **不改变任何功能与验收要求**：FR-05 的两条通路、级联实现与第 6 节的验收指标都不变；变的只是
  论证时引用的数字。

## 1. 项目目标
建设一个基于 Python 的法律知识库系统，统一管理法律原始资料、条款版本、专业 Wiki、检索与辅助问答。

**系统遵循以下优先级：**

```
数据与权限安全 → 证据可靠 → 时间及适用范围匹配 → 回答准确 → 可解释与可追溯 → 响应速度
```

**核心原则**：允许增加检索、验证和人工审核时间，不允许为追求速度跳过必要的证据与权限检查。

### 1.1 核心目标
- 保存可核验的原始资料和来源信息
- 支持法律文件及条款的历史版本查询
- 提供精确检索、关键词检索、语义检索和图谱增强检索
- 提供带具体依据、适用条件和不确定性说明的问答
- 建立支持引用、修订、审核和更新提醒的 Wiki
- 实现访问控制、关键操作审计及备份恢复
- 建立持续评测与回归测试机制

### 1.2 系统边界

**定位**：本系统是**法律信息辅助工具**，面向律师、企业法务及法律研究人员，解决法律法规与裁判文书分散存储、版本难以追踪、人工检索效率低和问答结果缺乏依据的问题，构建支持文档解析、智能检索、法律问答与答案溯源的知识库，不是法律服务提供方。

**数据范围**：系统只存放**公共法律数据**（法律法规、司法解释、公开裁判文书），**不存放任何客户资料与具体案件数据**。第一版为**单租户、部门级内部工具**；SaaS 多租户属远期规划（见 1.3、FR-15）。

系统提供法律资料管理与研究辅助，**不将模型输出标记为未经审核的最终专业意见**。

**不构成法律意见**：系统输出（含检索结果、Wiki 内容与问答结论）不构成法律意见，不得作为对外出具法律结论的依据，也不替代执业律师的判断。系统须在界面与导出物上明示这一边界。

**以下事项不属于第一版目标：**

- 自动代理诉讼或执行外部法律行为
- 无人审核发布 AI 生成的专业知识
- 自动解决所有法律冲突及复杂适用性问题
- 全法域、全类型法律资料的完整覆盖
- 多智能体自主工作流
- 大规模分布式图数据库（图谱增强检索按《系统设计文档》第 8.4 节分阶段引入，概念验证阶段不新增常驻组件）
- 自动微调法律大模型

### 1.3 分阶段交付

第一版不一次性交付完整系统，分为三个可独立验收的阶段：

| 阶段 | 交付范围 | 不开放的能力 |
| --- | --- | --- |
| A：开发基础 | 数据库迁移、Wiki 草稿与修订、基础审计、任务状态 | 正式发布、真实敏感资料、多用户使用 |
| B：受控知识库 | 正式认证授权、原文与版本、解析校正、Wiki 审核、检索 | 未经验证的自动法律结论 |
| C：证据约束问答 | 澄清、生成、引用检查、主张核验、拒答与人工复核 | 未审核的自动外部法律行为 |

阶段 A 的开发身份机制不构成正式认证。进入阶段 B、接入真实受限资料或开放其他用户前，必须完成认证授权及必要安全验收。

各阶段与设计实施计划（P0–P7）的对应关系见《系统设计文档》17.2。

**第一版形态**：单租户、部门级内部工具，只接入公共法律数据；目标是跑通“原生解析 → 检索（含 GraphRAG 概念验证）→ 证据约束问答”的闭环。SaaS 多租户属远期规划（V2.0），引入前须满足《系统设计文档》第 18 节触发条件。

## 4. 功能需求

### FR-01 资料来源管理
系统应支持：

- 来源登记、可信等级和授权说明
- 官方原文、转载材料、内部分析等来源类型区分
- 来源地址、发布机关、抓取时间和更新频率记录
- 来源更新检查失败告警
- 来源被撤回、文件被替换或内容发生变化的记录

**约束条件：**

- 不得仅凭文件标题判断权威性
- 每份资料应显示“来源最后核查时间”，不得把资料入库时间当作来源更新时间

### FR-02 资料导入与原始文件保存
支持第一版约定格式的 **PDF、DOCX、HTML 和纯文本**资料。

**导入流程应包含：**

1. 文件类型、大小和完整性检查
2. 恶意文件及异常内容检测
3. 文件哈希及重复检测
4. 来源、权限和敏感级别登记
5. 原文件保存
6. 异步解析及任务状态反馈

**约束条件：**

- 导入失败必须保留原因，允许修复后重试
- 不能产生重复发布记录

### FR-03 文档解析与校正
**系统应提取：**

- 文档标题、章节、条款及正文
- 页码、段落、表格与附件关系
- 原文与解析文本之间的定位关系
- 解析器及 OCR 版本
- 质量检查结果与人工校正记录

**质量要求：**

- 保存原始解析结果，不以人工校正覆盖唯一原件
- 对条号、日期、金额、否定词、表格等设置重点检查
- 低质量解析进入待复核状态
- 无法可靠定位的片段不得伪造页码或字符位置
- 未通过质量门禁的内容不得进入正式问答证据范围

### FR-04 法律文件与条款版本管理
**系统应分别管理：**

- 法律文件的稳定身份
- 法律文件的各个版本
- 条款稳定身份
- 条款在各版本中的文本
- 改号、合并、拆分、替代及删除关系

**时间记录：**

- **业务时间**：公布、生效、失效等时间
- **系统时间**：采集、确认、修正和入库时间

**系统应支持：**

- 指定日期查询候选适用版本
- 历史版本对比
- 条款变更关系浏览
- 未知日期、资料缺口和适用性争议提示
- 过渡条款及特殊适用规则关联

**约束条件：**

- 不得仅依靠日期区间，自动宣告复杂问题的适用法律已经确定

### FR-05 搜索与检索
**检索入口：**

- 法律名称、文号、条号精确查询
- 关键词查询
- 自然语言语义查询
- 图谱关联检索（按条款关系、引用关系扩展相关依据）
- 历史版本查询
- 来源、法域、类型、时间及权限范围筛选

**结果应显示：**

- 资料名称、类型和来源
- 条款或原文片段
- 版本及状态
- 原文位置
- 来源核查时间
- 适用性或质量警告

**约束条件：**

- 默认保留用户原始查询，查询改写只能补充，不得静默改变金额、时间、主体和法律关系

### FR-06 证据约束问答

**问答流程应支持：**

1. 提取问题中的事实及条件
2. 识别缺失信息
3. 必要时提出澄清问题
4. 检索授权范围内的候选依据
5. 补齐相关定义、例外和引用条款
6. 生成候选答案
7. 执行引用与主张核验
8. 输出答案、有限回答、澄清请求、拒答或转人工结果

**正式答案至少包含：**

- 回答结论
- 已采用的事实或假设
- 关键依据
- 适用条件与限制
- 尚不能确定的事项
- 具体引用及原文入口
- 生成时间和知识范围说明

**严格禁止：**

- 编造文号、条号或引用
- 将资料库未找到等同于法律上不存在
- 将案例中的个别结论直接包装为普遍规则
- 将 Wiki 总结替代原文证据
- 把模型自报置信度作为可靠性证明

### FR-07 拒答与人工复核

系统应区分以下状态：

| 状态 | 含义 |
| --- | --- |
| ANSWERED | 在明确范围内完成回答 |
| PARTIAL | 部分问题可回答，其他部分说明限制 |
| NEEDS_CLARIFICATION | 缺少会改变结论的事实 |
| INSUFFICIENT_EVIDENCE | 未找到足够支持材料 |
| NEEDS_REVIEW | 存在冲突、高风险或适用性疑问 |
| FAILED | 技术故障，不能伪装成证据不足 |

**人工复核触发条件：**

- 具体责任认定
- 个性化期限计算
- 金额计算
- 未解决的依据冲突

风险规则应可配置，并记录触发原因。

### FR-08 Wiki 知识管理

**Wiki 应支持：**

- 专题、概念及术语页面
- 分类、别名和页面间链接
- 断言级引用
- 修订历史、差异对比及回滚
- 编辑、审核、发布及撤回
- 反向引用及更新影响查询

**发布状态：**

```
草稿 → 待审核 → 已发布
             ↘ 退回修改
已发布 → 已撤回
```

**依据状态：**

```
已核验 / 来源有更新 / 待复核 / 依据不足
```

**约束条件：**

- 已发布修订不可直接覆盖
- 回滚应创建新的修订和发布记录
- AI 可以生成草稿，不得自动成为正式知识

### FR-09 更新影响管理

来源或法律版本变化时，应执行以下流程：

1. 保存新版本
2. 标记受影响条款
3. 找出引用该条款的 Wiki 断言
4. 找出受影响的缓存及问答记录
5. 标记待复核
6. 通知相关责任人
7. 经审核后重新发布

**约束条件：**

- 既有回答应保留“当时使用的证据快照”
- 再次查看时应提示证据已更新

### FR-10 认证与授权

**第一版应实现：**

- 登录、退出、会话失效和用户禁用
- RBAC（基于角色的访问控制）
- 文档级和 Wiki 级访问控制
- 管理员强认证
- 失败登录限制
- 下载、导出、审核和发布的独立权限

**安全约束：**

- AI 不得决定用户有权访问哪些资料
- 权限变更后，即使检索索引尚未更新，也不得继续把受限内容发送给模型或用户

### FR-11 审计与追溯

**应记录以下操作：**

- 资料导入、校正及版本调整
- 权限变化
- Wiki 提交、审核、发布及撤回
- 问答所用证据、模型和配置
- 敏感下载和批量导出
- 审计配置及保留政策变化

**隐私保护：**

- 审计内容默认不保存访问令牌、密钥及不必要的敏感正文

### FR-12 评测与反馈

**系统应支持：**

- 人工金标准测试集管理
- 检索、回答、版本及安全专项测试
- 用户反馈与错误分类
- 配置变更前后对比
- 回归测试及发布门禁

**测试要求：**

- 测试集应拆分开发集和独立验收集
- 避免反复调参使验收结果失真
- 评测数据从 P0 阶段开始准备，不到问答阶段才建立

### FR-13 资源受限运行模式

系统应支持资源受限运行模式，在不跳过权限与证据核验的前提下，通过排队、降低并发、缩小计算批次和延迟执行控制资源消耗。

**系统应支持：**

- 用户可查看任务的排队、执行、失败和完成状态
- 批量入库和本地问答可按配置互斥
- 失败任务可重试

**约束条件：**

- 重型任务不得无限并发
- 模型加载失败、显存不足或系统内存不足时，应记录明确原因
- 重试不得重复生成版本或重复发布内容
- 资源不足时允许返回待处理状态，不得伪装为“未找到法律依据”
- 不得为节约资源静默删除例外条款、减少引用检查或跳过人工审核规则

### FR-14 合规与使用边界

**产品定位：**

- 系统是法律信息辅助工具，不提供法律服务，不替代执业律师判断
- 界面与导出物须明示“不构成法律意见”及系统能力边界
- 不得以系统输出直接对外出具法律结论

**数据来源合规：**

- 优先使用官方渠道公开资料；非官方来源须取得授权
- 每个来源须登记授权说明与最后核查时间；未登记授权说明的来源不得入库
- 采集须遵守目标站点的服务条款与访问限制，不得绕过技术措施，不得高频抓取
- 不得仅凭文件标题判断权威性

**引用溯源：**

- 正式输出中的每条关键依据必须可追溯到具体资料版本与原文位置
- 不得虚构文号、条号、页码或字符位置；无法定位时显式标注未知

**人工审核与责任边界：**

- 未通过质量门禁的内容不得进入正式问答证据范围
- 高风险结论必须经人工审核后才能对外使用
- 提供错误反馈入口；更正须留痕并通知受影响范围
- 不得把模型自报置信度作为可靠性证明

**约束条件：**

- 合规要求不因部署轻量化而降低

### FR-15 数据边界与准入

**数据范围：**

- 系统只存放公共法律数据（法律法规、司法解释、公开裁判文书），不得存放客户资料、案件卷宗、合同或其他主体数据
- 第一版为单租户、部门级内部工具；SaaS 多租户属远期规划，引入前须满足《系统设计文档》第 18 节触发条件

**数据准入网关：**

- 解析完成后、入库前须经脱敏节点；识别到当事人姓名、身份证号、案号、联系方式等实体时替换为占位符
- 脱敏须**先定位、后脱敏**：定位信息基于原件文本，脱敏后的入库文本与原件之间的映射关系须保留
- 实体映射表按最高敏感级别管理，访问权限严于业务数据，读写均写入审计
- 检索时先经映射表把查询词转换为占位符，再检索脱敏后的库；命中后是否回显明文由用户权限决定
- 脱敏漏检视为泄露风险，须经质量检查与人工校正；脱敏动作须留痕
- 不得以“数据已公开”为由免除脱敏与访问控制
- 含个人信息的文书原件须登记为受限范围（原件仅对显式授权者开放），由脱敏后的解析产物承担公开检索视图
- 姓名类实体需要 NER 能力，第一版正则识别器不覆盖；NER 就位前不得把解析产物作为对外发布内容

**租户与隔离：**

- 公共法条全局共享一份，不按租户复制；公共数据表不设组织字段
- 用户私有数据（问答历史、内部模板等）按租户隔离，落库前须明确归属
- 客户个性化问答采用临时检索：借用知识库的检索与推理能力，客户数据不落库
- 审计只记录元数据与哈希，不记录请求或回答正文

**约束条件：**

- 数据边界不因部署轻量化或功能扩展而放宽
- 数据分级、外发审批与模型调用策略须在接入真实资料前确认（需求 2.2）

### FR-16 多轮追问

**目标：**

- 同一会话内的追问能继承上文，用户不必重复已说过的条件（「那如果是这样呢？」）

**会话边界（不可放开）：**

- 上文**只用于补全检索查询**；模型输入仍只含本次检索到的条文原文与证据编号，**不得把历史问答放进提示词**
- 会话历史属于主体数据，**只进短期缓存**（脱敏后、TTL 到期即焚），**不落主库**；主库不新增会话表
- 每条追问产生**独立的问答运行**，须各自通过引用核验与合规声明门禁；**会话整体不构成正式输出**
- 会话只对**提交者本人**可见；越权访问按不存在处理（不泄露「存在但无权」）

**约束条件：**

- 短期缓存未配置时**多轮不可用，但单轮问答须照常可用**（不因会话功能缺失挡住主链路）
- 会话标识不得出现在 URL 中（与「问题文本不进 URL」同口径）
- 上下文**只取最近一轮**；**不实现指代消解**（规则不可靠，模型推断违反上一条边界）

## 5. 非功能需求

以下为建议目标，须经评审和压测确认。

| 类别 | 要求 |
| --- | --- |
| 准确性 | 关键主张必须有可核验证据；证据不足时降低回答范围 |
| 安全性 | 默认拒绝未授权访问，敏感数据不得未经审批外发 |
| 完整性 | 原文、版本、引用和关键审计可追溯 |
| 可维护性 | 模块化单体、显式接口、数据库迁移及版本锁定 |
| 可观测性 | 请求、问答、任务、证据和配置可通过追踪 ID 关联 |
| 可恢复性 | 备份必须通过恢复演练 |
| 性能 | 搜索与问答分开设定目标，不以速度替代核验 |
| 可访问性 | 常用页面支持键盘操作及清晰的错误反馈 |

### 5.1 性能要求

第一阶段优先保证任务完整性、可追踪性和回答质量。性能目标按语料规模、扫描件比例、模型部署方式及查询类型分别测量，不将不同配置结果混合比较。

| 项目 | 要求 |
| --- | --- |
| 任务受理 | 快速返回任务 ID，不等待完整解析或模型推理 |
| 精确查询 | 单独测量 P50、P95 |
| 混合检索 | 与精确查询分别统计 |
| 自动问答 | 区分排队、模型冷启动、检索、生成和核验时间 |
| 人工审核 | 不计入自动处理耗时 |
| 超时处理 | 返回状态和追踪入口，不丢失任务 |
| 性能验收 | 使用约定语料和配置建立基线后，再确定正式阈值 |

> **说明**：以下数值是试验目标，不是上线保证，需在基线测量后重新确认：普通检索 P95 ≤ 5 秒；问答任务受理 ≤ 2 秒；自动核验问答 P95 ≤ 120 秒。
>
> 准确性指标（第 6 节）不因开发设备资源受限而降低。

### 5.2 备份与恢复要求

- 开发阶段必须提供数据库和原文件备份操作流程，并完成恢复测试
- 仅保存于同一块内部 SSD 的副本，不作为独立故障恢复副本
- 恢复优先级：法律原文、数据库及密钥优先；派生索引允许恢复或重建

RPO、RTO 在配置独立备份目标并完成演练后确定。在此之前，以下时间值仅为规划目标，不对外承诺：

- **核心数据库目标 RPO**：不超过 1 小时
- **核心数据库及原文访问目标 RTO**：不超过 8 小时
- **全量检索恢复时间**：另行通过索引恢复或重建演练确认

## 6. 验收标准

建议首版建立不少于 **300 条人工审定问题**，覆盖历史版本、例外、事实缺失、无答案、权限和恶意输入等场景。具体数量按业务复杂度调整。

### 6.1 质量指标

| 验收项目 | 初始目标或要求 |
| --- | --- |
| 依据 Recall@20 | 宏平均 ≥ 0.85，按人工标注条款版本计算 |
| 前五结果精度 | 目标 ≥ 0.75，明确相关性及去重定义 |
| 关键主张支持率 | 人工评估目标 ≥ 0.95 |
| 发布引用完整性 | 不存在、越权或无法定位的引用一律拦截 |
| 应拒答问题处理率 | 目标 ≥ 0.90 |
| 可回答问题错误拒答率 | 目标 ≤ 0.10 |
| 版本专项 | 预设关键版本错误案例不得漏过门禁 |
| 权限专项 | 测试中不得出现越权泄露 |
| 合规专项 | 正式输出物均含“不构成法律意见”声明；每个来源均有授权说明与核查时间 |
| 溯源专项 | 正式输出的关键依据 100% 可定位到具体版本与原文位置 |
| 审计 | 故障测试后业务、审计和事件记录可对账 |
| 恢复 | 完成至少一次数据库、原文及索引恢复演练 |

### 6.2 报告要求

- 报告样本量、分母、分组结果及不确定性
- 不得只报告平均值，隐藏高风险类别失效
- 数字达标不代表对所有真实问题正确
- RAGAS 指标单独标识，不与传统检索指标混用

> **说明**：RAGAS 的 LLM-based Context Recall 可基于参考答案主张进行评估，定义不同于文档级 Recall@K。参考：[docs.ragas.io](https://docs.ragas.io)
